# Five-stage drop detection - auto-derived parameters, per span

Generated by `python Pipelines/drop_motifs/run_drop5_report.py`.

**What this is for.** Every parameter below was derived from the signal rather than hand-tuned, and this report exists so the derivation can be graded span by span. Each row carries my own verdict and the reason for it; correcting those verdicts is the feedback that will improve the derivation.

## How the parameters are derived

Two parameters are time-scaled and everything else in the detector is dimensionless by construction (`slope_sigma` is a multiple of the noise, `min_depth_frac` a fraction of the deepest fall, the window multipliers fractions of the fall). Both derive from the span's **feature width** - the lag at which its autocorrelation falls to half height, which measures how wide one event is rather than how far apart events are:

- `segment_seconds = width / 5`
- `detrend_window_s = width x 10`
- `min_separation_s = 0.25 x the measured event spacing`, applied once to the chosen pass

The width was chosen over the period by measurement against the six previously hand-tuned spans: `segment / width` spreads 4x across them and clusters at ~0.2, while `segment / period` spreads 51x. A period is the spacing *between* events; a segment has to resolve the *inside* of one. Mushroom_260720 is the case that forces the distinction - its icicles are ~50 s and spaced ~1400 s apart, so a period-derived segment made the icicle smaller than one segment and the detector returned zero events on a recording with twenty-six of them.

The width is then **refined from the detections themselves** - the median event extent of what came back - because a frequency-modulated span has no single stationary scale for any estimator to find. Three candidate scales are tried first (the lobe width and two fractions of the period), the best is refined, and the best is the one finding the most events among passes whose events do not overlap each other.

**Annotated counts are a check, never an input.** No parameter is derived from them, so a span matching its annotated count is evidence rather than arithmetic.

## How to read the verdict

The headline metric is **window purity**: the detector's own slope gate is re-run *inside* each stored window and the qualifying falls are counted. A correctly extracted window holds exactly 1. The defect this work addresses scored 3.

| verdict | meaning |
|---|---|
| PASS | >=90% of windows hold exactly one fall, and any annotated count matches |
| SUSPECT | 60-90% clean, or the count disagrees with a human |
| FAIL | <60% clean, or nothing found |

An autocorrelation confidence below 0.5 is noted on the row: it means the scale came from refinement rather than from the seed, which is not itself a problem but is worth knowing when judging why a span behaved as it did.

## The motif library

Every extracted window is persisted under `motifs/` as `motifs.csv` (the index), `motifs.npz` (the arrays) and `manifest.json`. Each row carries `purity` and `is_pure`, so a consumer can take the clean subset without re-running detection, and `raw_mv` / `detrended_mv` / `t_s` are stored per motif. Keys lead with the catalogue ID because two spans here are sub-spans of two others on the same recording (ID 20 inside ID 1, ID 21 inside ID 3), and a recording-and-onset key would collide between them.

The format is the one `cluster.py` and `gradients.py` already read, which is why every figure above is drawn from the library rather than from the detection run that produced it - a figure drawn from one and a library written from the other is the class of mistake that produces a plot nobody can reproduce.

## What to change if a span is wrong

| symptom | knob | where |
|---|---|---|
| segments too coarse; events missed whole | `SEGMENTS_PER_FEATURE` | `Working/Detection/drop_motifs/autoparams.py` |
| the detrend ate the event (amplitudes far too small) | `DETREND_FEATURES` | same |
| one event reported as several | `DEDUP_INTERVAL_FRAC`, or a coarser segment | same |
| windows hold a neighbour | `window_cap_mult`, `window_pad_frac`, `TIGHTEN_STEPS` | `detect5.py` |
| junk events with no real rise | `min_rise_frac` | `Detect5Params` |
| events where something bigger is in frame | `min_fall_dominance` | `Detect5Params` |
| wrong morphology chosen | `morphology='sharkfin'` or `'trough'` | `Detect5Params`, per span |
| too few / too many falls pass the gate | `slope_sigma` | `Detect5Params` |
| onset lands before the real drop | `trough_knee_frac` | `refine_onset` in `detect5.py` |

Every one of these can be set per span without touching the derivation, by passing it through `autotune(..., **overrides)`.
